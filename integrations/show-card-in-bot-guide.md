# 💳 نمایشِ شماره‌کارت داخلِ خودِ ربات — راهنمای پیاده‌سازی برایِ پلتفرم‌های ربات

این راهنما برایِ **توسعه‌دهندگانِ پلتفرم‌هایِ ربات/پنل** است: چطور به‌جایِ فرستادنِ مشتری به صفحه‌ی وبِ پرداختِ CubePay (`pay_page_url`)، مبلغ و شماره‌کارت را مستقیماً داخلِ همان چتِ رباتِ فروشنده نشان بدهید — **بدونِ هیچ تغییری سمتِ CubePay**، چون این دیتا از قبل تویِ جوابِ همان endpointِ ساختِ فاکتور هست، فقط تا امروز استفاده نمی‌شد.

---

## 🧠 ایده در یک خط

فروشنده از پنلِ رباتِ مدیریت (`@cubepy_bot`) یه تنظیمِ روشن/خاموش داره: «نمایشِ شماره‌کارت داخلِ ربات». وقتی روشنه، جوابِ ساختِ فاکتور شاملِ `show_card_in_bot: true` + خودِ آبجکتِ `card` می‌شه — یعنی دیگه لازم نیست کاربر رو به یه صفحه‌ی وبِ خارجی بفرستید، همون تویِ پیامِ رباتتون مبلغ و کارت رو نشون بدید.

## ⚙️ کجا فعال می‌شه؟

خودِ فروشنده از داخلِ `@cubepy_bot`: «⚙️ تنظیماتِ بیشتر → 💳 روش‌هایِ پرداخت → 🤖 روشن‌کردنِ نمایشِ کارت در ربات». این یه تنظیمِ حسابیه، نه پارامترِ درخواست — شما فقط جوابِ API رو چک می‌کنید، خاموش/روشن‌کردنش دستِ خودِ فروشنده‌ست.

## 📥 فیلدهایِ مربوطه در جوابِ ساختِ فاکتور

چه از endpointِ توصیه‌شده (`POST /pay/create-order.php`) استفاده کنید چه از قدیمی‌ترِ کارتی‌ (`POST /smspay/api/create-payment.php`)، همین فیلدها تویِ جواب هست:

```jsonc
{
  "success": true,
  "method": "card",
  "authority": "bdc9e0497c121d6187750d53798dae81",
  "pay_page_url": "https://cubevps.ir/pay.php?authority=...",   // فالبک، اگه show_card_in_bot=false بود همینو باز کنید
  "pay_amount_toman": 216928,        // دقیقاً همین عدد — نه مبلغِ درخواستی‌تون
  "show_card_in_bot": true,          // تنظیمِ حسابِ فروشنده — تصمیم با خودشه
  "card": {
    "number": "6104XXXXXXXX1234",
    "holder": "نامِ صاحبِ کارتِ فروشنده",
    "sheba": null                    // اگه null بود، دکمه/خطِ شبا رو اصلاً نشون ندید
  },
  "expires_at": "2026-09-24T13:45:00+03:30",
  "expires_in_minutes": 15
}
```

## ✅ قوانینی که نباید بشکنه

1. **همیشه دقیقاً `pay_amount_toman` همینِ جواب رو نشون بدید، نه مبلغِ درخواستی‌ی خودتون.** این عدد شاملِ چندتومنِ اضافه‌ی «یکتاساز» است که تشخیصِ خودکارِ پیامکِ بانکی رو ممکن می‌کنه — اگه مبلغِ گردِ خودتون رو نشون بدید، تاییدِ خودکار انجام نمی‌شه.
2. **آبجکتِ `card` رو از هیچ فاکتورِ قبلی کش نکنید.** اگه فروشنده چرخشِ کارت داره، هر فاکتور ممکنه کارتِ متفاوتی بگیره — همیشه همون `card` که تویِ جوابِ *همین* فاکتور اومده رو نشون بدید.
3. **`show_card_in_bot` رو خودتون هارد-کد نکنید.** همیشه از جوابِ API بخونیدش؛ اگه `false`/`null` بود، به‌جاش `pay_page_url` رو بفرستید (لینکِ صفحه‌ی وبِ پرداخت) — این تصمیمِ فروشنده‌ست، نه شما.
4. **تاییدِ پرداخت هیچ فرقی نمی‌کنه.** فارغ از اینکه کارت رو تو ربات نشون دادید یا صفحه‌ی وب باز کردید، همون `authority` رو برایِ `POST /smspay/api/verify-payment.php` یا poll‌کردنِ کال‌بک استفاده کنید — مکانیزمِ تشخیص و تاییدِ پیامکِ بانکی کاملاً مستقلِ از نحوه‌ی نمایشه.
5. **شبا فقط برایِ انتقالِ آنی.** اگه `card.sheba` مقدار داشت، حتماً همراهش یه هشدارِ کوتاه بدید («فقط اگه انتقالتون آنیه از شبا استفاده کنید») — پایا/ساتنایِ معمولی ممکنه دیر برسه و فاکتور منقضی بشه.

## 💬 نمونه‌ی قالبِ پیام (تلگرام، HTML)

```
💳 <b>پرداخت</b>
مبلغ: <b>{pay_amount_toman}</b> تومان

شماره‌کارت: <code>{card.number}</code>
به نام: {card.holder}

⚠️ مبلغ را دقیقاً همین عدد واریز کنید — تاییدِ خودکار فقط با همین رقم انجام می‌شود.
⏳ این فاکتور تا {expires_in_minutes} دقیقه‌ی دیگر معتبر است.
```

(اختیاری ولی پیشنهادی: قبل از نشون‌دادنِ این پیام، یه تاییدِ «متوجه شدم» از کاربر بگیرید — دقیقاً همون الگویی که تو صفحه‌ی وبِ خودِ CubePay هم اضافه شده، برایِ کم‌کردنِ واریزهایِ اشتباه.)

## 🚀 چرا این‌جوری و نه یه endpointِ جدا؟

چون هیچ endpointِ جدیدی لازم نیست — دیتا از قبل تویِ همون جوابِ ساختِ فاکتوره. کارِ شما فقط اینه که به‌جایِ ریدایرکت‌کردنِ خودکار به `pay_page_url`، یه شرط بذارید: اگه `show_card_in_bot` بود، همون دیتا رو تویِ پیامِ خودتون رندر کنید.
