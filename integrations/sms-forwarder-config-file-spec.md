# قراردادِ فنی — واردکردنِ خودکارِ تنظیمات در CubePay SMS Forwarder (اندروید)

> این سند جوابِ سشنِ بک‌اند/بات است به درخواستِ هماهنگی برای «ویزاردِ تلگرام
> + فایلِ تنظیماتِ رمزنگاری‌شده». نتیجه‌ی بررسی: **ایده‌ی اصلی خوب است، ولی
> رمزنگاری با کلیدِ ثابتِ داخلِ اپ رد شد** — دلیلش پایین‌تر. طرحِ جایگزین هم
> کدِ کمتری می‌خواهد هم امن‌تر است.

> **بروزرسانی ۱.** بخشِ ۵ (کارِ لازم سمتِ اپ) پیاده و تست شد: دکمه‌ی «وارد
> کردن از متن» در صفحه‌ی اصلی، پارسِ schema v1، و صفحه‌ی مرور/تأییدِ
> همیشگیِ فیلتر قبل از ذخیره (کامیتِ `323f148`).

> **بروزرسانی ۲ — تصمیمِ نهایی عوض شد به کدِ یک‌بارمصرف (بخشِ ۳، نسخه‌ی
> دوم).** صاحبِ کسب‌وکار به‌جای پیستِ متنِ JSON، طرحِ توکن/کد را انتخاب کرد
> — تا حتی اگر خودِ چتِ تلگرام هم لو برود، رازِ HMAC همراهش نباشد. اپ طبقِ
> همین قرارداد پیاده و کامپایل (هر سه فلیور) و پوش شد (کامیتِ `d44c80b`).
> جزئیاتِ سمتِ اپ:
>
> - **ورودی:** دیالوگِ «وارد کردن از متن» یک فیلدِ متنی دارد که هم کد
>   (رشته‌ی ۱۶ تا ۶۴ کاراکترِ `A-Za-z0-9_-`) هم لینکِ کامل
>   (`https://cubevps.ir/smspay/import.php?t=<TOKEN>`) را می‌شناسد. اگر
>   هیچ‌کدام نبود، به‌عنوانِ متنِ خامِ JSON (مسیرِ قبلی، برای تست/توسعه)
>   پارس می‌شود — یعنی چیزی حذف نشد، فقط مسیرِ کد/لینک اولویت دارد.
> - **درخواست:** `GET https://cubevps.ir/smspay/import.php?t=<TOKEN>` با
>   HTTPS (بدونِ هیچ هدرِ اضافه). جوابِ موفق: `{"success":true,"config":{...schema v1...}}`.
>   جوابِ ناموفق: `{"success":false,"reason":"invalid"|"expired"|"used"}` —
>   هر سه پیامِ فارسیِ جداگانه به فروشنده نشان می‌دهند («کد منقضی شده»،
>   «قبلاً استفاده شده»، «معتبر نیست»)، همه با راهنماییِ «از بات یه کدِ
>   تازه بگیر».
> - **deep link:** روی `MainActivity` یک `intent-filter` برای
>   `https://cubevps.ir/smspay/import*` ثبت شد (VIEW + BROWSABLE +
>   DEFAULT، بدونِ `autoVerify` چون سمتِ سرور `assetlinks.json` نداریم —
>   یعنی لمسِ لینک با یک chooser باز می‌شود، نه خودکار؛ برای این مورد
>   کافی است). اگر فروشنده مستقیم روی لینکِ توی چتِ تلگرام بزند، اپ باز
>   می‌شود و بدونِ نیاز به کپی/پیستِ دستی همان لحظه واکشی را انجام می‌دهد.
> - بقیه دست‌نخورده: صفحه‌ی مرور/تأییدِ همیشگیِ فیلتر قبل از ذخیره (رازِ
>   HMAC آنجا نشان داده نمی‌شود)، پرسیدنِ سیم‌کارت بعدِ تأیید اگر
>   `source == SMS`، و فیلترِ واردشده همیشه **اضافه** می‌شود نه جایگزین.
>
> از این طرف چیزِ دیگری لازم نیست — بات می‌تواند شروع کند به ساختِ
> endpoint طبقِ همین قرارداد و فرستادنِ لینک/کد در چتِ خصوصی.

---

## ۱) آیا اپ الان می‌تواند تنظیمات را وارد کند؟

**نه، هنوز نه.** این کارِ جدید است. مدلِ داده‌ی اپ (`FilterRule`،
`WebhookTarget`، `ForwardTarget`) از قبل متدِ `fromJson`/`toJson` دارد —
یعنی زیرساختِ سریالایز کردن آماده است، فقط صفحه‌ای برای **وارد کردن** از
بیرون وجود ندارد. کارِ لازم در بخشِ ۵ دقیق آمده.

---

## ۲) قالبِ دقیقِ داده — با اصلاح نسبت به پیشنهادِ اولیه

طرحِ اولیه دو جا با کدِ واقعیِ اپ نمی‌خواند؛ اگر همان‌طور پیاده می‌شد، بدنه‌ی
وب‌هوک ساخته می‌شد ولی پلیس‌هولدرها جایگزین نمی‌شدند (چون `{message_body}`
یک توکنِ ناشناخته است):

| پیشنهادِ اولیه | چیزی که واقعاً در کد هست |
|---|---|
| `{message_body}` | `{msg}` |
| `{received_at}` | `{time}` |
| هدرِ امضا: ۲ تا | **۳ تا**: `X-CubePay-Timestamp`, `X-CubePay-Sender`, `X-CubePay-Signature` |
| مقدارِ امضا | `sha256=<hex>` — با پیشوند، نه فقط hex |
| `"body_type": "form"` | enum واقعی: `FORM_URLENCODED` یا `JSON` |

**ساده‌سازیِ مهم:** اگر `bodyTemplate` خالی بماند، اپ خودش همین الان
فرمِ پیش‌فرضِ درست را می‌سازد (`text`, `sender`, `received_at`, به‌علاوه‌ی
امضای HMAC خودکار). یعنی **قالب اصلاً لازم نیست در قرارداد باشد** — فقط
`url` و `secret` کافی است. این هم ریسکِ ناهماهنگیِ توکن‌ها را کاملاً حذف
می‌کند، هم قرارداد را کوتاه‌تر.

### schema نهایی (v1)

```json
{
  "v": 1,
  "filter": {
    "name": "بلوبانک",
    "source": "SMS",
    "senders": "9999987641",
    "keywords": "به حساب شما نشست",
    "logic": "OR"
  },
  "webhook": {
    "url": "https://cubevps.ir/smspay/webhook/sms.php",
    "secret": "<رازِ HMAC فروشنده>"
  },
  "forwardNumber": null
}
```

| فیلد | نوع | توضیح |
|---|---|---|
| `filter.source` | `"SMS"` \| `"NOTIFICATION"` | اگر بانک با نوتیفیکیشن می‌فرستد (مثلِ بلوبانک) نه پیامک |
| `filter.senders` | رشته، با ویرگول جدا | همان چیزی که در `sendersRaw` می‌نشیند — بدونِ تغییرِ فرمت |
| `filter.keywords` | رشته، با ویرگول جدا، اختیاری | ترجیحاً یک عبارتِ کاملِ مشترکِ بینِ همه‌ی نوع‌های پیامکِ آن بانک (مثلِ نمونه‌ی بالا)، نه یک کلمه‌ی کوتاه که با کلماتِ دیگر قاطی شود |
| `filter.logic` | `"OR"` \| `"AND"` | پیش‌فرض `OR` |
| `webhook.secret` | رشته | همان رازی که همین امروز هم در پنل نشان داده می‌شود |
| `forwardNumber` | رشته یا `null` | اختیاری — شماره‌ی فورواردِ پیامکِ پشتیبان |

**چیزی که عمداً در schema نیست: `simSlot`.** انتخابِ سیم‌کارت
دستگاه‌به‌دستگاه فرق می‌کند (شماره‌ی اسلاتِ سیم۱/سیم۲ در دو گوشیِ مختلف
لزوماً یکی نیست) — بات نمی‌تواند از قبل بداند. اپ بعد از وارد کردن، اگر
`source == SMS` بود، از فروشنده می‌پرسد کدام سیم — همان الگویی که همین
الان در صفحه‌ی فیلتر وجود دارد.

## ۳) رمزنگاری — پیشنهادِ کلیدِ ثابت رد شد

**کلیدِ ثابتِ داخلِ APK امنیتِ واقعی نمی‌دهد.** فایلِ APK عمومی و
قابلِ‌دانلود است (لینکِ مستقیم، بازار، احتمالاً بعداً گوگل‌پلی) و باز کردنِ
آن با ابزارهایی مثلِ `jadx` چند دقیقه کار است. هر کلیدی که داخلِ اپ
باشد، عملاً یک رمزِ عمومی است — یعنی هر کسی که APK را داشته باشد
می‌تواند **رازِ HMAC هر فروشنده‌ای** را از فایلِ رمزگذاری‌شده‌اش دربیاورد.
و رازِ HMAC چیزِ کوچکی نیست: هر کسی آن را داشته باشد می‌تواند وب‌هوکِ جعلی
با امضای معتبر بسازد و «واریز» تقلبی به سرورِ فروشنده تحویل بدهد. رمزنگاری
با کلیدِ ثابت این ریسک را **کم نمی‌کند، پنهان می‌کند** — بدتر از رمزنگاری
نکردن، چون حسِ امنیتِ دروغین می‌دهد.

### پیشنهادِ جایگزین: بدونِ رمزنگاری، با همان مرزِ اعتمادِ فعلی

امروز هم راز از طریقِ چتِ خصوصیِ تلگرام (بات ↔ فروشنده) به‌صورتِ متن‌بازِ
عادی نشان داده می‌شود — همان‌جا مرزِ اعتماد است، نه فایل. پیشنهاد:

**نسخه‌ی اول (بسازید، کمترین ریسک و کمترین کد):**
بات همان JSON را به‌عنوانِ یک بلوکِ متن در همان چت می‌فرستد. فروشنده کپی
می‌کند، در اپ باز می‌کند («تنظیمات ← وارد کردن از متن»)، پیست می‌کند. اپ
یک صفحه‌ی مرور نشان می‌دهد («این فیلتر و این آدرسِ وب‌هوک اضافه بشه؟» —
رازِ HMAC در این صفحه دیده نمی‌شود، فقط آدرس، نامِ فیلتر و فرستنده) و
فروشنده تأیید می‌کند.

- بدونِ رمزنگاری، بدونِ کلید
- بدونِ مجوزِ جدید (نه دوربین، نه فایل)
- مرزِ امنیتی همانی است که امروز هم وجود دارد (چتِ خصوصیِ تلگرام)
- فیلترِ جدید **همیشه اضافه می‌شود، هیچ‌وقت فیلترِ موجود را جایگزین یا حذف نمی‌کند**

**نسخه‌ی دوم (تصمیمِ نهایی — بروزرسانی ۲ در بالا را ببینید):**
بات به‌جای متنِ کامل، یک لینکِ کوتاه‌عمر و یک‌بارمصرف می‌فرستد
(`https://cubevps.ir/i/<توکن>`). اپ لینک را با یک deep link باز می‌کند،
از همان توکن با HTTPS خودِ JSON را می‌گیرد، توکن سمتِ سرور بعدِ اولین
استفاده یا بعدِ ۱۰ دقیقه باطل می‌شود. رازِ HMAC هیچ‌وقت داخلِ خودِ لینک
نیست، فقط بعدِ اعتبارسنجیِ توکن، از سرور به اپ می‌رسد. این دقیق‌تر است
ولی به یک endpoint سمتِ سرور و یک intent-filter در اپ نیاز دارد — کارِ
اضافه که فعلاً لازم نیست.

**QR کد را پیشنهاد نمی‌کنم:** اپ الان اصلاً مجوزِ دوربین ندارد. اضافه
کردنش یک مجوزِ حساسِ تازه است — دقیقاً همان نوع چیزی که چند هفته پیشِ ما
را درگیرِ Play Protect کرد. برای حلِ یک مشکلِ تایپی، ارزشش را ندارد.

## ۴) چه چیزی خودکار پر شود، چه چیزی داخلِ اپ بماند

| | خودکار از فایل | داخلِ اپ (بعد از وارد کردن) |
|---|---|---|
| آدرسِ وب‌هوک، راز | ✅ | |
| فرستنده، کلمه‌ی کلیدی | ✅ | |
| منبع (SMS/نوتیفیکیشن) | ✅ | |
| سیم‌کارتِ دریافت/ارسال | | ✅ — دستگاه‌به‌دستگاه فرق دارد |
| تأییدِ نهایی | | ✅ — چیزی بی‌صدا اعمال نمی‌شود |

## ۵) کارِ لازم سمتِ اپ (تخمین)

- یک صفحه‌ی جدید: فیلدِ پیست‌کردنِ متن → پارس با همان الگوی
  `FilterRule.fromJson`/`WebhookTarget.fromJson` (با گسترشِ کوچک برای این
  schema) → کارتِ مرورِ خلاصه (بدونِ نمایشِ رازِ خام) → دکمه‌ی تأیید
- بعدِ تأیید، اگر `source == SMS`، همان پرسیدنِ سیم‌کارتی که الان در
  ساختِ دستیِ فیلتر هست
- ذخیره به‌عنوانِ یک `FilterRule` **جدید** در کنارِ فیلترهای موجود
- اعتبارسنجی: آدرس باید `https://` باشد (همان تابعِ `isValidHttpsUrl`ی
  که از قبل هست)؛ اگر JSON خراب یا ناقص بود، خطای روشن نشان بدهد، نه
  شکستِ بی‌صدا

هیچ‌کدامِ این‌ها به تغییر در فرمتِ خودِ وب‌هوک یا امضای HMAC نیاز ندارد —
آن بخش از قبل کار می‌کند و دست‌نخورده می‌ماند.

## خلاصه برایِ بات (بروزشده — نسخه‌ی توکن‌دار)

یک endpoint بسازید: `GET https://cubevps.ir/smspay/import.php?t=<TOKEN>`
— توکن ~۳۲ کاراکترِ url-safe، یک‌بارمصرف، حدودِ ۱۵ دقیقه معتبر. جوابِ
موفق: `{"success":true,"config":{...schema بالا...}}` (فقط `filter`,
`webhook{url,secret}`, `forwardNumber` — بدونِ `bodyTemplate`). جوابِ
ناموفق: `{"success":false,"reason":"invalid"|"expired"|"used"}` (با
HTTP 200، نه کدِ خطا). بعدِ یک بار استفاده‌ی موفق، توکن باید `used` شود.

در چتِ خصوصی به فروشنده لینک/کد بدهید:
`https://cubevps.ir/smspay/import.php?t=<TOKEN>` — روی لمسِ همین لینک
اپ خودش باز می‌شود و واکشی می‌کند؛ یا فروشنده می‌تواند خودِ کد/لینک را در
اپ («وارد کردن از متن») پیست کند. رمزنگاری و QR لازم نیست — راز اصلاً
داخلِ خودِ لینک/کد نیست، فقط بعدِ اعتبارسنجیِ توکن از سرور به اپ می‌رسد.
