# بسته‌های اتصال CubePay — درگاه کارتی عادی

سه بسته مستقل برای PHP، Python و Node.js؛ مطابق قرارداد فعلی `smspay/api/create-payment.php` و `verify-payment.php`.
این بسته‌ها جایگزین اجباری اتصال‌های قبلی نیستند و روی اپ اندروید تغییری ایجاد نمی‌کنند. مسیر رمزارز در این نسخه بسته‌ها پیاده نشده است.

## انتخاب بسته

| پوشه | پیش‌نیاز | ساخت فاکتور از خط فرمان |
|---|---|---|
| `php` | PHP 8.1+، cURL و PDO SQLite | `php example.php create ORDER-unique 200000 BUYER-ID https://your-shop.example/callback` |
| `python` | Python 3.10+؛ بدون کتابخانه اضافی | `python example.py create ORDER-unique 200000 BUYER-ID https://your-shop.example/callback` |
| `node` | Node.js 22.13+ با node:sqlite | `node example.mjs create ORDER-unique 200000 BUYER-ID https://your-shop.example/callback` |

دو متغیر محیطی سمت سرور را تنظیم کنید: `CUBEPAY_TOKEN` توکن همان فروشنده و `CUBEPAY_DB` مسیر مطلق یک دیتابیس SQLite خصوصی و ماندگار **بیرون public_html**. برای هر فروشنده دیتابیس جداگانه داشته باشید؛ نمونه‌ها چندفروشنده‌ای نیستند. از SQLite روی فایل‌سیستم اشتراکی شبکه‌ای استفاده نکنید. پوشه دیتابیس باید از قبل وجود داشته و تنها برای کاربر سرویس قابل خواندن باشد.

فایل example یک ابزار CLI است و مسیر وب ایجاد نمی‌کند. در سایت یا ربات خودتان کلاس Store را وارد کنید؛ نمونهٔ واقعی اتصال به مسیر وب پایین آمده است. مقدار، خریدار و کال‌بک از سفارش ثبت‌شده در سمت سرور شما گرفته شوند، نه از درخواست آزاد مشتری. هر `order_id` فقط برای یک سفارش واقعی استفاده شود.

### واحد مبلغ

آرگومان `amount_rial` برحسب **ریال** است؛ ۲۰٬۰۰۰ تومان = ۲۰۰٬۰۰۰ ریال. برای تبدیل از تابع `tomanToRial` / `toman_to_rial` استفاده کنید؛ عدد اعشاری پذیرفته نمی‌شود. `pay_amount` مبلغ نهایی قابل واریز، شامل سهم کارمزد مشتری و افست است و باید عیناً نمایش داده شود. مقدار `amount` در پاسخ verify ممکن است شامل سهم کارمزد مشتری باشد، ولی افست را شامل نمی‌شود؛ بنابراین با قیمت خام محصول یکی نیست.

Store شناسه پرداخت، مبلغ اولیه، مبلغ نهایی و خریدار را قبل از تحویل ذخیره می‌کند. نتیجه verify باید به همان شماره سفارش تعلق داشته باشد و مبلغ آن در محدودهٔ مبلغ اولیه تا مبلغ نهایی ثبت‌شده باشد. مقدار سفارش قابل تحویل از دیتابیس خودتان خوانده می‌شود.

## برگشت از درگاه

در مسیر HTTPS کال‌بک، فقط `authority` را از درخواست JSON/فرم/کوئری دریافت کنید؛ `order_id`، مبلغ، شناسه خریدار و `success` ورودی، مدرک پرداخت نیستند. authority را به `Store.callback` بدهید. کلاس، فاکتور ذخیره‌شده را پیدا می‌کند و با توکن فروشنده از API بررسی می‌کند. شناسه ناموجود رد می‌شود.

نمونه Flask در برنامهٔ موجود شما:

```python
@app.route('/cubepay/callback', methods=['GET', 'POST'])
def callback():
    payload = request.get_json(silent=True)
    if payload is None:
        payload = request.form or request.args
    if not hasattr(payload, 'get'):
        return {'success': False}, 400
    authority = payload.get('authority', '')
    if not isinstance(authority, str) or len(authority) != 50:
        return {'success': False}, 400
    store = Store(os.environ['CUBEPAY_DB'], CubePay(os.environ['CUBEPAY_TOKEN']))
    try:
        state = store.callback(authority)
        return {'success': state in ('paid', 'sandbox_paid'), 'state': state}
    finally:
        store.db.close()
```

در Express، پس از فعال کردن parser محدود JSON/فرم، همان authority را به `await store.callback(authority)` بدهید؛ در PHP به `$store->callback($authority)`. هیچ فرمان shell را با ورودی کال‌بک نسازید. پاسخ JSON `success:true` فقط برای `paid` یا `sandbox_paid` است؛ دومی فقط نتیجه آزمایشی است و تحویل واقعی ندارد. برای خطای موقت پاسخ 503 بدهید و جزئیات توکن/پاسخ خام را به مشتری نشان ندهید.

## تحویل دقیقاً یک سفارش

Store هنگام تأیید، وضعیت سفارش و **یک ردیف** در `delivery_outbox` را در یک تراکنش ثبت می‌کند. کال‌بک تکراری، اجرای دوبارهٔ برنامه و تأیید دوباره، ردیف تحویل دوم ایجاد نمی‌کنند. خریدار و مبلغ این ردیف از سفارش محلی گرفته می‌شود.

بسته خودش سرویس مشتری یا موجودی فروشگاه شما را تغییر نمی‌دهد. برای تحویل:

1. پردازشگر فروشگاه ردیف `queued` را بخواند.
2. اگر موجودی و سفارش در همین دیتابیس‌اند، افزایش اعتبار و علامت `done` روی outbox را **در یک تراکنش**، با قید یکتای `order_id` انجام دهید.
3. اگر تحویل از یک API خارجی است، `authority` را کلید idempotency بفرستید و مقصد باید این کلید را یکتا enforce کند. تنها بعد از ثبت موفق تحویل، outbox را `done` کنید. صرف داشتن outbox برای تضمین یک‌بارگی اثر جانبی در API فاقد idempotency کافی نیست.

## قطع ارتباط و وضعیت نامعلوم

API فعلی verify فقط بار اول موفق می‌شود. پاسخ HTTP 409 یعنی قبلاً verify شده، اما **مبلغ تأییدشده در آن پاسخ نیست**. اگر برنامه بعد از verify و قبل از ثبت محلی قطع شود، تبدیل خودکار 409 به پرداخت موفق امن نیست. Store چنین سفارش‌هایی را `reconcile` نگه می‌دارد؛ `verifying` باقی‌مانده پس از توقف برنامه هم باید بررسی شود. تا تطبیق با سابقه معتبر درگاه، تحویل ندهید و از مشتری هم درخواست پرداخت دوباره نکنید.

ساخت فاکتور نیز در خطای شبکه نتیجه نامعلوم دارد. بسته دوباره و خودکار create نمی‌زند؛ شناسه سفارش در دیتابیس باقی می‌ماند و ساخت تکراری محلی متوقف می‌شود. ثبت جدید با شماره سفارش دیگر برای دور زدن این حالت، ممکن است دو فاکتور بسازد.

`unpaid` پایان قطعی بررسی نیست: ممکن است رسید دیرهنگام همان فاکتور بعداً دستی تأیید شود. در صورت رسیدن کال‌بک جدید، Store همان authority را دوباره استعلام می‌کند.

## قابلیت‌های دیگر

در `create` می‌توانید `customer_user_id` و `customer_username` را بفرستید. شناسه خریدار فقط از دادهٔ معتبر سایت/ربات خودتان بیاید. توکن در مرورگر، APK، URL یا مخزن عمومی قرار نگیرد. TLS اعتبارسنجی می‌شود و درخواست احراز هویت‌شده redirect را دنبال نمی‌کند.

راهنمای کاربران: [CubePay Help](https://cubevps.ir/panel/help/). بسته‌های قدیمی حذف نشده‌اند. این نسخه یک نمونهٔ قابل اجرا با ذخیره پایدار است؛ اتصال مرحله تحویل به محصول شما همچنان لازم است.
